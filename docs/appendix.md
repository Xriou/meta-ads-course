## A1 · CRM→CAPI 回传架构精要


> 🎯 **本节目标：** 浓缩课程第九章的工程精华：CRM 业务状态如何可靠地变成 Meta 事件，分「状态检测→事件生成→队列→发送」四层。


### 📖 讲解

<p><b>核心概念。</b>State（状态，如「已合格」）vs Event（状态第一次转换的瞬间）；State Machine（允许的状态跳转路径表）；Event Record（业务事件的存证）与 Transmission Log（发送记录）分离；Event Queue（异步发送队列，失败可重试）。</p><p><b>数据流图（文字＋箭头，四层）。</b></p><p>CRM 状态变更 ──▶ ① 状态差检测（比对 Previous/Current）── 仅当「首次转换」──▶ ② 生成 Event Record（存证）──▶ ③ 入 Event Queue（异步）── 退避重试 ──▶ ④ Meta 发送 ＋ 写入 Transmission Log（发送记录）</p><ul><li><b>① 状态差检测层：</b>每日定时跑任务，对比每条 CRM 记录的 Previous 状态与 Current 状态。只有「状态首次前进」（如 待定→Qualified）才生成事件；回退（Qualified→待定）不生成。失败模式：没存 Previous 快照 → 每次都误判为「首次」→ 重复事件。</li><li><b>② Event Record 层：</b>业务事件的存证（谁、什么时候、从什么变到什么），与发送分离。失败模式：只发不存 → 出问题无法审计、无法补发。</li><li><b>③ Event Queue 层：</b>异步发送队列，削峰＋解耦＋可靠。失败模式：同步直发 → 发送端一挂，事件永久丢。</li><li><b>④ 发送＋日志层：</b>带 event_id 发送，记录 Transmission Log（事件 ID/发送时间/响应码/重试次数）。失败模式：无 Transmission Log → 无法回答「Meta 收到没」。</li></ul><p><b>核心字段表（每个事件必备）。</b></p><ul><li><b>event_id</b>：事件唯一身份证＝CRM Record ID ＋ 状态名（如 LEAD-88231-Qualified），保证去重一致性（同一记录同一状态只算一次，L0-03 双通道机制）。</li><li><b>event_name</b>：语义名（Lead / Qualified / Purchase），标准事件优先。</li><li><b>event_time</b>：业务发生时间（用状态变更时间，而非发送时间）。</li><li><b>crm_id / user_info</b>：用户标识（哈希后的 email/phone），供 Meta 匹配回画像、拉高 EMQ（L0-03）。</li><li><b>value / currency</b>：业务价值（如 Qualified 预估 LTV $1,200），让模型学「高价值人群」。</li><li><b>hash 字段</b>：em（邮箱 SHA-256）、ph（手机 SHA-256），CAPI 侧必传以拉 EMQ。</li></ul>


### ⚙️ 底层机制

<p>为什么不能「销售点个按钮就发事件」：①状态回退会产生假事件（Day 5 又点一次 Qualified=重复，污染模型）；②同步发送失败即丢信号（无队列则宕机即丢）；③无存证则无法审计（出事查不出）。正确架构＝状态变更检测→生成 Event Record→入 Queue→带重试发送→记录 Transmission。这四层对应 L0-03 的「Signal 才是模型真正学的」，事件不可靠＝信号不可靠。</p>


### 🛠️ 实操清单

<p><b>最小可行方案。</b></p><ul><li>① CRM 状态字段＋变更历史表（存 Previous/Current）。</li><li>② 每日定时对比 Previous/Current 状态，首次转换才生成事件。</li><li>③ Event ID＝CRM Record ID＋状态名（保证去重一致性，MSG 433）。</li><li>④ 发送失败退避重试（1h/6h/24h，见 A2）。</li></ul><p><b>四层失败模式对照表（自检用）：</b></p><ul><li>检测层漏＝重复事件；存证层漏＝无法审计；队列层漏＝宕机丢事件；日志层漏＝无法对账。</li><li>深度工程（DLQ/幂等）见课程第九章原文与附录 A2。</li></ul>


### 💼 实战案例

<p><b>演练：工业设备账户的 Qualified 回传修复。</b></p><ul><li>修复前：CAPI 只发 Lead/Purchase，Qualified 漏发 3 个月 → 模型「半聋」，真实 Qualified CPL 被虚高 70%（见 L11-01）。</li><li>修复动作：加「状态差检测」任务（比对 Previous/Current），首次 待定→Qualified 才生成 Event Record（event_id＝LEAD-88231-Qualified），入 Queue 退避发送，写 Transmission Log。</li><li>结果：上线 3 天后后台 Qualified 率从 22% 爬到 33%，真实 Qualified CPL 从 $30.3 降到 $24.2；Day 5 回退（Qualified→待定）未发事件，Day 30 重新合格发新事件（新 event_id，MSG 433 合规）。</li></ul>


### ⚠️ 常见错误

<ul><li>重复事件（状态回退未防）——污染模型、虚增转化；</li><li>Event ID 不稳定（去重失效）——双通道算成两次；</li><li>发送无存证（出问题无法审计）——丢数据无人知；</li><li>同步直发（失败即丢）——宕机即永久丢失。</li></ul>


### 🧪 自测

**Q：** 客户状态 Day 5 从 Qualified 改回「待定」，Day 30 又改回 Qualified。系统应该发几次事件？

<details>
<summary>点击查看答案</summary>

Day 5 回退不发（回退不是新的合格瞬间）；Day 30 重新合格=一次新的状态转换→可发新事件，但 Event ID 必须与第一次不同（同一 Record 的第二次 Qualified 是新事件，MSG 433 的标准答案：Day 30 可以产生新的 Qualified Event，且不能继续使用第一次的 Event ID，否则会被 L0-03 去重机制判为同一事件而丢弃）。

</details>


### ✅ 掌握标准

能画出「状态变更→事件生成→队列→发送」四层图并指出每层的失败模式，并写出你账户的 Qualified 事件字段表。


### 📌 来源与实战印证

<p>论坛无对应工程实践（社区停留在手工导入导出）；各类报错处理本质是「无架构时代的手工补丁」。此附录是 B2B 投放从「会投」到「体系化」的分水岭——把销售系统的状态变化变成模型可学的可靠信号。</p>

## A2 · Event Queue / Retry / 传输日志


> 🎯 **本节目标：** 掌握回传系统的可靠性三件套：队列化、退避重试、全链路日志，并把发送过程建模成状态机。


### 📖 讲解

<p><b>可靠性三件套的协同。</b></p><ul><li><b>Queue（队列）</b>：削峰（营销活动导致的状态变更洪峰）＋解耦（业务系统与 Meta API 互不拖死）＋可靠（失败不丢）。</li><li><b>Retry（退避重试）</b>：指数退避 1h→6h→24h，叠加随机扰动（Jitter）避免「重试风暴」打爆 API。</li><li><b>Transmission Log（传输日志）</b>：必录事件 ID / 发送时间 / 响应码 / 重试次数 / 最终状态。</li></ul><p><b>发送状态机（State Machine）。</b></p><p>Pending（入队未发）──▶ Sending（发送中）── 成功 ──▶ Sent（Meta 已确认）<br>　　　│　　　　　　　　　　　│── 失败（可重试：5xx/限流 429）──▶ Retrying（按退避计时）<br>　　　│　　　　　　　　　　　│── 失败（不可重试：4xx 字段非法）──▶ Dead（进 DLQ 人工）<br>　　　└─ Retrying 重试耗尽（>3 次）──▶ Dead（DLQ）</p><ul><li><b>可重试错误</b>：网络超时、Meta 限流（429）、5xx。进 Retrying，按 1h/6h/24h 退避＋Jitter。</li><li><b>不可重试错误</b>：字段校验失败（4xx 业务错误）、event_id 非法。直接进 Dead Letter Queue（DLQ），人工修数据后重发。</li></ul><p><b>幂等设计（为什么重复发送无害）。</b>每个事件带稳定 event_id；Meta 侧按 event_name＋event_id 去重（L0-03 双通道机制）。即便因重试导致「发送两次」，Meta 也只记一次。幂等的关键：event_id 在重发时不变（不能用发送时间当 ID）。另：业务侧重发前先查 Transmission Log 该 event_id 是否已是 Sent，避免无谓重试。随机扰动（Jitter）确保一批失败事件不会在同一秒集体重试，压平 API 峰值。</p>


### ⚙️ 底层机制

<p>「事件发生」和「事件送达」是两件事：必须分开记录才能回答「Meta 为什么没收到」——是没生成（业务侧）、没发送（网络侧）、还是没匹配（Meta 侧，EMQ 低）。这是第八章 Debugging 框架（MSG 424）的工程基础。没有状态机，你无法区分「正在重试」与「已死」；没有幂等，重试会制造重复事件——两者缺一不可。</p>


### 🛠️ 实操清单

<p><b>监控面板三指标。</b></p><ul><li>队列深度（积压＝业务洪峰或 API 故障）：告警线 >1 天工作量。</li><li>发送成功率：告警线 <95%。</li><li>Meta 侧 Event Received 对账（周度）：业务侧 Sent 数 vs Meta 收到数，差额 >5% 即查 EMQ/去重。</li></ul><p><b>退避参数表：</b>第 1 次失败 1h 后重发、第 2 次 6h、第 3 次 24h、第 4 次（仍失败）进 DLQ。每次重试叠加 0–300s 随机 Jitter。</p>


### 💼 实战案例

<p><b>演练：服务器宕机 2 小时的事件丢失测试。</b></p><ul><li>场景：周一发现上周五服务器宕机 2 小时，期间 30 个 Qualified 状态变更。</li><li>架构 A（Event Record 与 Transmission Log 分离＋队列）：宕机只影响「发送」，恢复后队列自动补发（带重试），30 个事件未丢，周一上午全部 Sent。</li><li>架构 B（同步直发且无存证）：这 30 个事件永久丢失，只能从 CRM 状态历史人工补发（且易重复）。</li><li>结论：状态机让「正在重试」可见、「已死」可捞；分离架构让宕机≠丢数据。</li></ul>


### ⚠️ 常见错误

<ul><li>失败后无限快重试（触发限流 429，雪崩）——应指数退避＋Jitter；</li><li>无对账（丢数据无人知）——业务侧 Sent 与 Meta Received 必须周度比对；</li><li>日志缺失时间戳（无法排查时序问题）——Transmission Log 必录发送时间＋响应码；</li><li>用发送时间当 event_id（破坏幂等）——重试变重复事件。</li></ul>


### 🧪 自测

**Q：** 周一发现上周五的服务器宕机 2 小时，期间 30 个 Qualified 状态变更。事件丢了吗？

<details>
<summary>点击查看答案</summary>

取决于架构：若事件生成（存证）与发送分离且进队列——宕机只影响「发送」，恢复后队列自动补发（带重试），事件未丢（对应 A2 状态机的 Pending/Retrying 自愈）；若同步直发且无存证——这 30 个事件永久丢失，只能从 CRM 状态历史人工补发。这正是「Event Record 与 Transmission Log 分离」的价值（与 A1 四层架构呼应）。

</details>


### ✅ 掌握标准

为你的回传链路补上三件套（Queue/Retry/Log）与发送状态机，或写明现有链路的可靠性缺口（DLQ/幂等/对账是否齐备）。


### 📌 来源与实战印证

<p>论坛对应物为零（纯工程领域）；但「Meta 收到了吗」的困惑社区高频存在（数据对不上）——本附录就是那个困惑的系统级答案。社区手工补发的本质，就是把本该由 Queue＋Retry 自动做的事人肉化了。</p>

## A3 · Data Dictionary / Event Schema 规范


> 🎯 **本节目标：** 建立字段级的数据字典：让每个事件的每个字段「只有一个含义」，并用 Schema 版本化管理跨事件复用。


### 📖 讲解

<p><b>Data Dictionary 的核心纪律。</b>所有事件的字段清单（名称 / 类型 / 含义 / 取值范围 / 负责人）集中管理；一个字段一个含义，跨事件复用不许变义（「标准变了」＝历史数据报废，MSG 355–356）。Schema 版本化：v1/v2 记录变更日期与理由，历史数据不改。新增字段走评审（谁提/谁审/影响面）。</p><p><b>三个核心事件的 Schema 示例。</b></p><p><b>① Lead 事件（询盘提交）。</b></p><ul><li>event_id：CRM Lead 号（如 LEAD-88231），唯一。</li><li>event_name：Lead（标准事件）。</li><li>event_time：表单提交时间（UTC）。</li><li>crm_id：CRM 记录号。</li><li>em / ph：哈希用户邮箱/手机（拉 EMQ，L0-03）。</li><li>content_name：产品/表单名。</li><li>value / currency：预估询盘价值（如 $300 / USD），可选但建议传。</li><li>lead_source：渠道标记（Meta / Google / 直接）。</li></ul><p><b>② Purchase 事件（成交，CRM 回传）。</b></p><ul><li>event_id：CRM Deal 号（如 DEAL-5521），与 Lead 不同事件、不同 ID 空间。</li><li>event_name：Purchase（标准事件）。</li><li>event_time：成交时间。</li><li>crm_id / em / ph：同 Lead 的用户标识（用于跨事件匹配同一人）。</li><li>value / currency：真实成交额（如 $3,200 / USD），必传。</li><li>order_id：订单号。</li><li>product_category：品类（用于细分分析）。</li></ul><p><b>③ Qualified 事件（合格询盘，CRM 状态转换回传）。</b></p><ul><li>event_id：CRM Record ID ＋ 状态名（如 LEAD-88231-Qualified），保证「同一 Lead 的第二次 Qualified 是新 ID」（MSG 433）。</li><li>event_name：Qualified（自定义或标准 Lead 的进阶，建议自定义以区分）。</li><li>event_time：状态变更为 Qualified 的时间。</li><li>crm_id / em / ph：用户标识。</li><li>value / currency：预估 LTV（如 $1,200 / USD），让模型学高价值人群。</li><li>qualifier：判定人/销售（审计用）。</li><li>industry / region：行业档/地区档（A3 字段字典的复用字段，含义固定）。</li></ul>


### ⚙️ 底层机制

<p>为什么 Schema 一致性 > 字段数量：模型与你的分析都依赖「同样的输入=同样的含义」。字段乱义的后果是双重的——回传信号失真＋内部报表不可比。Data Comparability（口径可比）是跨时间/跨市场分析的前提（MSG 356–358）。一个字段两个含义，等于把历史数据悄悄废掉——这是比「少一个字段」更贵的错误。</p>


### 🛠️ 实操清单

<p><b>落地四步。</b></p><ul><li>① 先建字典（哪怕只有 10 个字段），每个字段写清名称/类型/含义/取值范围/负责人。</li><li>② Schema 版本化（v1/v2 变更记录＋生效日期），历史数据不改。</li><li>③ 新增字段走评审（谁提/谁审/影响面：依赖此字段的报表与回传逻辑）。</li><li>④ 季度审计：抽 20 条真实事件对照 Schema 检查合规率（目标 ≥95%）。</li></ul><p><b>字段变更＝口径事件：</b>走版本管理（L6-13 原则在数据层的落地），通知所有消费方（CRM 报表/回传脚本）。</p>


### 💼 实战案例

<p><b>演练：给 Qualified 事件的「行业」字段增加两个新取值。</b></p><ul><li>影响面评估：历史事件此字段分布、依赖此字段的报表（行业维度 Qualified 率）/回传逻辑。</li><li>Schema 升版：v1→v2，记录变更日期与理由（如新增「新能源/工程机械」两档）。</li><li>历史数据不改（保留原口径），新取值从生效日启用。</li><li>通知消费方：CRM 报表、CAPI 回传脚本、Meta 事件映射同步更新。</li><li>结果：跨时间对比时 v1 与 v2 分段清晰，不会出现「同一行业两种含义」的脏数据。</li></ul>


### ⚠️ 常见错误

<ul><li>同一字段多含义（不同人填不同东西）——历史数据报废；</li><li>Schema 随手改（无版本）——跨时间对比失真；</li><li>无字典（新人靠问老员工）——口径随人漂移；</li><li>字段越多越好论（低质字段污染）——少而准胜过多而乱。</li></ul>


### 🧪 自测

**Q：** 想给 Qualified 事件的「行业」字段增加两个新取值。正确流程？

<details>
<summary>点击查看答案</summary>

①评估影响面：历史事件此字段的分布、依赖此字段的报表/回传逻辑；②Schema 升版（v1→v2）记录变更日期与理由；③历史数据不改（保留原口径），新取值从生效日启用；④通知所有消费方（CRM 报表/回传脚本）。字段变更＝口径事件，走版本管理（L6-13 原则在数据层的落地，与 MSG 355–356 的「标准变更=历史报废」反向操作——用版本化避免报废）。

</details>


### ✅ 掌握标准

写出你核心 3 个事件（Lead/Purchase/Qualified）的 Schema 与字段字典初版（含字段名/类型/含义/负责人）。

<p>论坛无对应概念；各类术语帖是「社区字典」的雏形——同一个词大家理解一致才能协作，数据字段同理，只是要求更严格（字段错义会直接污染模型信号）。</p>

## A4 · 奇技淫巧与野路子打法（论坛实录）


> 🎯 **本节目标：** 看懂社区流行过的非标准打法：机制、兴衰与教训——理解即可，不建议照搬。


### 📖 讲解

四大流派：①一刀流（1-1-1 极低预算强拉，靠小幅加预算/开关挤量；「刀」=美金预算单位，衍生 10 刀流/万刀流/无刀流玩梗分级）；②小强打法（20 刀起、1-1-1、空投受众、自动化规则分层 +10% 加预算）；③结构命名流（111/11N/121/1NN = 系列-组-广告）；④玄学派（复制/开关重置学习期）。


### ⚙️ 底层机制

兴衰史最有教育意义：一刀流 2026 年 3–5 月有效（「数据又好又能花钱」）→6 月初风控一来集体崩盘（「一整个月都在亏钱」）→7 月基本废（「一刀死了之后账户跑不起来」，短剧玩家 ROI 从 0.4 掉到 0.2）。机理：低预算玩法依赖风控窗口，窗口关闭即反噬——垃圾流量（「CPM 低的厉害，进的全是垃圾」）、花不动、转点炸。


### 🛠️ 实操清单

可迁移的内核：①小强打法的「自动化规则分层加预算」（ROAS>3.5→+10%/小时、分层上限 $50/$100/$200/$300、不达标自动停）=正规可复用；②「横向激进纵向保守」（关快、建多、加慢）；③结构命名的控制变量思想（测素材 1-1-N、测受众 1-N-1、猛攻 1-1-1）；④「巨量怎么玩 FB 就怎么玩」的迁移心法。不可迁移：一切依赖风控窗口的钻空子部分。



### ⚠️ 常见错误

把玄学当方法论（复制重跑常归零）；只学一刀流的「形」不学小强的「神」（有新人被只教一刀流的师傅带废，「一刀没了就彻底不会测品」）；把玩梗分级（亿刀流）当真打法。

### 📖 讲解

### ⚙️ 底层机制

### ⚠️ 常见错误

黑话与标准语混用导致团队沟通歧义（「ASC」有人以为还是旧名）；把玩梗词（亿刀流）当正式术语写进文档；只懂黑话不懂机制（会背「吃素材」不知道为什么）。

## A6 · 高危警示区（论坛灰产实录）


> 🎯 **本节目标：** 认识社区里真实存在的高危玩法及其代价——定位是风险科普，不含任何操作手法。


### 📖 讲解

五大高危区（论坛真实讨论存在）：①仿牌 FP（卖侵权品；双封、TRO 律师函、国内代理拒接、「割一波换一波」）；②买卖/租赁广告户（号商生态、假企业户骗局、号被找回、盗刷局、跑路）；③养号 farm（指纹浏览器+独立 IP 批量养号、死号连坐）；④绕过验证（视频验证改图片、地区「过审」偏方，有效性低随时失效）；⑤博彩/Slot（H5/PWA、地区轮换、素材秒拒、盘总上下游）。


### ⚙️ 底层机制

真正的代价（社区原话实录）：封号封 BM 封支付通道是「常规操作」；资金冻结与追讨无门；「号商小泽被抓案」——抄家、蹲几年，这是灰产链顶端的结局样本。合规卖家的社区共识：「干掉灰的让我们吃口饭」。2026-06 风控潮证明：平台收紧时灰产首当其冲，波及的还有与灰产混谈的边缘打法（一刀流躺枪）。


### 🛠️ 实操清单

自卫清单：①只与合规 BSP/官方接口合作；②拒绝一切「代开/包过/资源号」推销；③资产自主（自有 BM/主页/像素，提前绑老 BM 切忌裸奔）；④收款通道合规（黑五死户潮的教训）；⑤发现合作方涉灰立即切割（连坐风险）。



### ⚠️ 常见错误

低估「连坐」（同 BM/同收款链一损俱损）；相信「别人做了没事」（幸存者偏差——被抓的不会再发帖）；为短期 ROI 引入灰产流量认知（把垃圾流量当「行业常态」）；把高风险打法与正规打法混在同一套资产里。


### 🧪 自测

<details>

①合法性层：买卖户+验证绕过属明确违规，法律风险真实（小泽案：抄家+刑责）；②经营层：户被找回/盗刷/跑路概率高，资产归零是常态而非尾部风险；③机会成本层：同样的钱与精力投在正规资产（自有 BM/素材/数据）会产生复利，灰产资产归零即清零。结论：不碰，且记录推销者避免牵连。

</details>

### ⚙️ 底层机制
